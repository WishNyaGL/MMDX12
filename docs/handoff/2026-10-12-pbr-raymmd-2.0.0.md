# 세션 핸드오프: 2.0.0 = 엔진 PBR + Ray-MMD 호환 재질 (2026-10-12)

새 세션(Opus)은 이 문서부터 읽고 시작하세요. 일정은 고려하지 않는 "완전 최종 2.0.0" 인수인계입니다. 이 문서가 담는 것: 결정과 그 이유,
이미 확인한 사실(출처 포함), 아직 확인하지 않은 것, 설계 제약, 작업 단위, 검증 방법, 해서는 안 되는 것.
먼저 `CLAUDE.md`, `AGENTS.md`(CLI 사용법은 매 실행 전에 읽을 것), `progress.md`의 최신 항목, 메모리(`MEMORY.md`)를 읽으세요.

## 0. 한 줄 요약

우리 엔진은 아직 "MMD 표면 + 셰이더 팩" 구조이고 PBR 재질 모델이 없다. 2.0.0은 **엔진에 재질별 PBR 경로를 넣고(알베도·노멀·거칠기·금속·AO·에미시브 +
셰이딩 모델), 그 PBR 값을 Ray-MMD 재질 데이터(`.emd` -> 재질 `.fx` -> `#define` 맵/값)와 glTF/VRM에서 채운다**. 셰이더 팩은 NPR 룩 전용으로 남고
Ray-MMD 지원의 수단이 아니다.

## 1. 왜 이 방향인가 (결정 이력)

1. 시작은 프로젝트 세카이(Sekai Model Pack v4, ps_* 모델)의 MME `.fx`를 앱에서 쓸 수 없다는 문제였다. MME 런타임(D3DX9 effect, ps_3_0, G-buffer / 모션벡터
   / RT / PT / GI와 양립 불가)은 만들지 않기로 했고(`progress.md` 2026-10-12), 클린룸 셰이더 팩 `project_sekai_toon`으로 갔다(온라인 갤러리 전용).
2. 그 과정에서 사용자가 두 번 짚었다. (a) 라이브러리는 사용자가 채우므로 폴더/파일 이름 구조에 의존하면 안 된다. (b) 특정 게임 전용 감지를 엔진에 하드코딩하고
   특정 팩 ID를 자동 적용하는 것은 틀렸다. 그래서 1.10.1에서 팩이 `pack.json "suggest"`로 조건을 선언하고 엔진은 **추천만** 하는 범용 메커니즘으로 바꿨다
   (메모리 `feedback-no-library-layout-assumptions`, `feedback-no-game-specific-engine-code`).
3. `library/by StarNoodle495` (캐릭터 12종, 폴더 16개) 조사에서 하나의 전용 셰이더로는 묶을 수 없다는 결론이 나왔다. 이 모델들은 평범한 PMX(추가 UV 0개, 스피어
   매트캡 + 공유 툰)이고, 작가가 의도한 룩은 **Ray-MMD PBR 재질**이다(readme: "미리보기를 재현하려면 Ray-MMD로 렌더링해야 한다"). 라이브러리에 Ray-MMD 재질
   `.fx`가 163개, 9개 세트(StarNoodle 8세트 + `stage/moonlit_waves`)로 있다. 캐릭터뿐 아니라 스테이지도 쓴다.
4. 사용자 결정: **어차피 필요한 PBR 지원 -> Ray-MMD 데이터 호환 PBR 기능을 엔진에 넣는다.** 팩 API v7을 새로 설계하는 대안은 버렸다. 이유: Ray-MMD 재질은
   스타일이 아니라 G-buffer에 값을 쓰는 순수 데이터이고(아래 3절), 조명은 이미 엔진이 하는 일이다. glTF/VRM의 PBR 맵도 같은 블록에 채울 수 있다.

## 2. 현재 엔진 상태 (이 작업의 출발점)

- 버전은 `CMakeLists.txt`의 `PROJECT_VERSION`. 이 핸드오프 작성 시점에 1.10.1이 커밋되어 있고 **릴리즈(GitHub / 델타 업데이트 / 사이트 / 갤러리)는 아직 안 했다.**
  1.10.1 릴리즈 여부는 사용자가 정한다(§9). 2.0.0은 그 위에서 시작한다.
- 표면 셰이딩: `shaders/mmd.hlsl` `PSMain`(~503행)은 MMD 방식(앰비언트 + 디퓨즈 × 광색, 툰 램프, 스피어 곱/가산, 스페큘러 파워). PBR이 없다. 거칠기·금속·노멀맵·AO
  개념이 없다. `PSPack`(~593행)은 팩의 `PackShade`를 호출한다.
- 레이트레이싱/패스트레이싱: `shaders/rt_common.hlsli`(RtGeometry 테이블, 바인드리스), `shaders/pathtrace.hlsl`(실시간 PT), `shaders/offline_gi.hlsl`(오프라인 GI).
  PT/GI는 확산 + MMD 스페큘러 근사다. **GGX 스페큘러 로브 샘플링이 없다.** 팩은 `PtPackOut.specular`(가산 복사휘도)로 근사한다(`docs/shader_pt_api.md`).
- 재질 상수: `MaterialConstants`(`src/render/ShaderInterop.h` 72행)는 **정확히 256바이트이고 빈 float가 없다.** 1.10.1에서 `packClass` 상위 비트(8..15)에
  `alphaKey`를 인코딩해 한 자리를 써 버렸다(`PackAlphaKeyFromClass`, `PackClassLow`). PBR 블록은 별도 상수 블록(또는 StructuredBuffer)이 필요하다.
  `RtGeometry`(같은 파일 180행)는 **192바이트 고정**이고, 패딩 `_padAddUv[3]` 중 `[0]`을 `alphaKey`로 썼다.
- 정점 스트림: `GpuVertex` 60B 고정. 추가 UV는 슬롯 4 사이드 스트림(`GpuAddUv`), RT는 바인드리스 raw 버퍼(`RtGeometry::addUvSrv`). **PMX는 탄젠트가 없다.** 노멀맵에는
  탄젠트 프레임이 필요하다: 래스터는 화면 미분(derivative) 기반, RT/PT는 삼각형 UV에서 계산하는 것이 현실적이다.
- 텍스처: 재질당 `srvTable`(텍스처 / 스피어 / 툰) 3칸. 재질 모프의 텍스처 계수(`texMul/texAdd` 등)가 있다. 팩 텍스처는 팩 전체 공용 최대 16개이고 **재질별 텍스처 개념이 없다.**
- glTF/VRM 가져오기(`src/asset/ImportScene.h`의 `ImpMaterial`)는 `baseColor`, 텍스처 하나, `emissive` 색, 두 플래그뿐이다. **금속-거칠기, 노멀, 오클루전, 에미시브 맵을 버린다.**
  PBR 블록이 생기면 여기서 채울 수 있다(범용성 근거).
- 셰이더 팩 시스템(API v6, `kPackApiVersion` 6, `docs/shader_pt_api.md`, `docs/shader_effect_api.md`, 사이트 문서)은 그대로 유지한다. 팩의 룩은 건드리지 않는다.
- MME 참조 읽기: `src/asset/MmeHints.*`가 모델 자신의 `.emd`(같은 stem, 없으면 폴더의 유일한 `.emd`) -> `.fx` -> `#include` -> `ResourceName`을 따라간다.
  이것이 Ray-MMD 파서의 출발점이지만 지금은 얼굴 SDF 하나만 찾는다.
- 모델 특성 / 추천: `asset/ModelTraits`, `ShaderPack::Suggests`, `characterShaderSuggested`. 팩이 `pack.json "suggest"`(`additionalUvsMin`, `toonMapMaterialsMin`)로 맞는 모델을
  선언하고 엔진은 토스트 + 선택 목록의 "추천" 표시로만 알린다(자동 적용 없음).
- 1.10.1에서 추가된 팩 `alphaKey`(`pack.json` 클래스 규칙, 해당 클래스 재질의 텍스처 R이 값보다 작으면 모든 렌더 경로에서 컷아웃)는 이번 PBR 작업과 무관하게 유지한다.

## 3. Ray-MMD 구조 (직접 확인한 부분)

출처: 라이브러리의 `by StarNoodle495/MovieSonicMMD_Ver2.0.2/Ray1.5.2Materials/FX/material_common_2.0.fxsub`(1598줄), 같은 폴더 `Body.fx` 등,
`AlcanderMMD/RayMaterial/RAY_FX/*.fx`, `.emd` 파일들. Ray-MMD 자체는 MIT 라이선스(구현 의미를 읽는 것은 문제없다. 코드를 복사해서 배포하지는 말 것).

- **재질 `.fx`는 색을 그리지 않는다.** 파일 하나가 `#define`들(맵 지정과 값)을 나열하고 `#include "material_common_2.0.fxsub"`(또는 `main.fxsub`)를 한다. 공통 파일의
  `MaterialParam`(447행) -> `EncodeGbuffer`(689행)가 `GbufferParam`(463행, `COLOR0..COLOR3` 4장)에 알베도, 노멀, 스무스니스, 메탈니스, 에미시브, 두께·곡률 등을 **인코딩**해
  쓴다. 조명(IBL, 광원, 반사, 그림자)은 Ray-MMD 컨트롤러(`ray.x` 쪽)가 G-buffer를 읽어 따로 계산한다. 즉 재질은 데이터이고 조명은 별개다.
- **셰이딩 모델 번호**(`material_common_2.0.fxsub` 63~73행): 0 DEFAULT, 1 SKIN, 2 EMISSIVE, 3 ANISOTROPY, 4 GLASS, 5 CLOTH, 6 CLEAR_COAT, 7 SUBSURFACE, 8 CEL, 9 TONEBASED,
  10 MASK. 재질은 `CUSTOM_ENABLE`로 번호를 지정하고, 에미시브 값이 임계(`EMISSIVE_EPSILON`)를 넘으면 EMISSIVE로 승격한다(`GetLightMode`, 1427행). 각 모델의 실제 계산식은
  컨트롤러 쪽에 있어서 **이 라이브러리 파일만으로는 알 수 없다.** 의미는 Ray-MMD 공개 소스/문서로 확정해야 한다(§6 P0).
- **맵 슬롯**: ALBEDO, ALBEDO_SUB, ALPHA, NORMAL, NORMAL_SUB, SMOOTHNESS, METALNESS, SPECULAR, OCCLUSION, PARALLAX, EMISSIVE, CUSTOM_A, CUSTOM_B. 각 슬롯에 `*_MAP_FROM`,
  `*_MAP_FILE`, `*_MAP_TYPE`, `*_MAP_SWIZZLE`, `*_MAP_UV_FLIP`, `*_MAP_APPLY_SCALE`, 슬롯별 `*_VALUE`, `*_MAP_LOOP`, `*_MAP_UV_SCALE` 등이 있다.
  `FROM` 값(확인한 범위): 0 없음(값 사용), 1 파일(`ResourceName`), 2 애니메이션 텍스처 파일, 3 PMX 재질 텍스처(MATERIALTEXTURE), 4 스피어 맵, 5 툰 맵, 6 화면 더미, 7/8은 재질 텍스처
  변형(정의는 있으나 의미 미확인). 값 4/5처럼 PMX 슬롯을 다른 용도로 재해석하는 점이 중요하다.
- **모프 연동**: `EMISSIVE_MAP_APPLY_MORPH_COLOR` 등은 `CONTROLOBJECT(self)`의 모프(`R+` `G+` `B+` `Blink` `Intensity+` `Intensity-`)로 에미시브를 제어한다. 우리 쪽은
  모델 모프 가중치로 매핑해야 한다.
- **`Cutout` 변형**(`material_common_2.0_Cutout.fxsub`, `main_Cutout.fx` 등)은 알파 컷아웃 재질이다.
- **`.emd`**: `Obj[i] = <fx 경로>`가 PMX 재질 순서(i)대로 재질 `.fx`를 지정한다. 한 모델에 `.emd`가 여러 개다. 예: `Alcander.emd`는 **SeriousShader**(일반 MMD용 `full.fx` 계열 기본 툰
  셰이딩, 8개 폴더에서 해시가 같은 파일)를 가리키고, `RayMaterial/RayMain.emd`와 `RayMaterialMap.emd`가 Ray 재질을 가리킨다. 사용자가 MMD에서 어느 것을 불러올지 고른다(`HowToUse.jpg`).
  Ray 재질 쪽 `.fx`가 참조하는 베이크 맵은 상대 경로(`../bodybake/bodybake_normal.png` 등)다.
- 라이브러리의 StarNoodle 재질 예(Alcander 몸 재질): 노멀 + 서브 노멀(모피), 스무스니스/메탈니스/스페큘러/오클루전/패럴랙스 파일, `CUSTOM_ENABLE 1`(스킨) + 곡률(`curve`)/두께(`thickness`) 맵.
  머리카락은 `CUSTOM_ENABLE 3`(이방성) + 머리카락 노멀. 눈은 에미시브 활성 + 스무스니스 맵.

## 5. 설계 방향 (결정된 것 / 열린 것)

**결정됨**
1. 엔진 코어에 **재질별 PBR 경로**를 넣는다. 팩 API v7은 만들지 않는다.
2. PBR 값의 출처는 둘이다: Ray-MMD 재질 데이터(이 문서의 중심), glTF/VRM의 PBR 맵(가져오기 개선). 둘 다 같은 내부 표현에 채운다.
3. **기본 룩은 절대 바뀌지 않는다.** PBR 경로는 데이터가 있고 사용자가 켠 재질/캐릭터에서만 쓴다. 기존 모델, 기존 팩의 룩은 비트 단위로 같아야 한다(메모리 `feedback-no-look-contamination`).
4. 사용자가 **재질 소스**를 고른다: 일반(기존) / Ray-MMD 재질 `.emd`. 후보 `.emd`는 **내용으로** 찾는다(모델 폴더 안의 `.emd` 중 `Obj[]` 개수가 PMX 재질 수와 맞고 가리키는 `.fx`가 Ray 재질인 것).
   직접 `.emd`를 지정하는 UI도 둔다. 폴더/파일 이름은 가정하지 않는다. 추천은 지금과 같이 토스트로 한 번만, 자동 적용 없음.
5. 선택은 캐릭터별 ini와 `.mmdxproj`에 저장한다(지금 셰이더 선택과 같은 방식).
6. 셰이딩 모델은 엔진에 직접 구현한다. 단계: DEFAULT, SKIN, EMISSIVE, ANISOTROPY(머리카락), GLASS -> CLOTH, CLEAR_COAT, SUBSURFACE -> CEL, TONEBASED, MASK는 필요할 때.
7. 이번 범위 밖: 모피 셸, 패럴랙스, `FireFog` 류 발광 효과, Ray-MMD 컨트롤러(IBL, SSR, 후처리)의 복제. 우리 렌더러의 라이팅으로 그리므로 Ray-MMD 렌더와 같은 화면은 나오지 않는다. 이것은 의도다.

**열려 있음 (새 세션이 판단)**
- PBR 블록의 저장 형식: 재질당 별도 StructuredBuffer와 바인드리스 텍스처 테이블(`RtGeometry`는 192B 고정이므로 새 레코드 + 인덱스)을 권장하지만 구현자가 결정.
- 맵 채널 패킹: 스무스니스/메탈니스/AO/스페큘러/두께/곡률을 로드 시 한두 장의 패킹 텍스처로 합칠지, 원본 SRV를 그대로 둘지(재질 52개 x 맵 여러 장이라 로딩 시간과 VRAM 문제가 실제로 생긴다). 중복 제거(같은 파일 공유)와 지연 로딩이 필요할 가능성이 높다.
- 래스터 노멀맵의 탄젠트: 화면 미분 vs 정점 스트림 추가. PMX에는 없으므로 정점 계산을 추가하면 `GpuVertex`(60B)를 건드린다. 건드리지 않는 쪽(미분 / 삼각형 UV)을 권장.
- PT/GI의 GGX 로브: 중요도 샘플링을 정식으로 넣을지, 1단계는 가산 근사로 둘지. 정식이 최종 목표다.
- 재질 모프(`R+`, `Blink` 등)와 기존 재질 모프(`texMul` 계열)의 상호작용.
- 선택 UI의 위치(메모리 `feature-placement-lobby`: 렌더에 영향을 주는 캐릭터별 옵션은 선택 화면의 패널에도 둔다).

## 6. 작업 단위 (일정 없음, 의존 순서만)

- **P0 의미 확정**: Ray-MMD 공개 소스/문서로 `FROM` 7/8의 의미, `*_MAP_TYPE`/`SWIZZLE`/`APPLY_SCALE`/`COLOR_FLIP`, 각 셰이딩 모델의 계산식, `CUSTOM_A`/`CUSTOM_B`가 모델별로 무엇을 뜻하는지
  (스킨 = 곡률/두께? 이방성 = 방향/세기?)를 확정한다. 이 라이브러리 안의 `fxsub`는 재질 쪽(인코딩)뿐이라 컨트롤러 쪽 식은 외부 소스가 필요하다.
- **P1 파서 + 프로브**: `asset/RayMaterial`(가칭). `.emd` -> `.fx` -> `#define` 평가(`#if`/`#include`/`#define` 정도의 얕은 전처리기) -> 재질별 `RayMaterialDesc`. `tools/raymat_probe`로 라이브러리
  163개 전체를 돌려 "읽히는 비율, 실제로 쓰이는 모드, 못 읽는 매크로"를 수치로 낸다. 폴더 구조에 의존하지 말 것. 못 찾는 파일은 경고만 하고 무시.
- **P2 엔진 연결**: 재질별 PBR 블록(상수 + 텍스처 테이블), 맵 로딩/중복 제거/지연 로딩, 모프 연동, RT용 레코드, 탄젠트, 알파(`ALPHA_MAP`), 기존 `MaterialConstants`/`RtGeometry`는 호환 유지.
- **P3 PBR 셰이딩(래스터 + RT)**: GGX 스페큘러, 메탈니스, 노멀 + 서브 노멀 블렌드, AO, 에미시브(+ 모프/블링크), 셰이딩 모델 DEFAULT / SKIN / EMISSIVE / ANISOTROPY / GLASS.
- **P4 PT / 오프라인 GI**: GGX 로브 샘플링과 나머지 모델(CLOTH, CLEAR_COAT, SUBSURFACE). `PtPackOut`/팩 경로와의 상호작용(PBR 재질 + 팩이 동시에 선택되면 규칙을 정할 것)을 문서화.
- **P5 사용자 기능**: 재질 소스 선택 UI(플레이 바 / 선택 화면 패널 / 스튜디오 인스펙터), 후보 `.emd` 탐색, 추천 토스트, 저장(ini / `.mmdxproj`), 4개 언어 i18n(`I18nEn/Ja/Zh.cpp`).
- **P6 glTF/VRM**: `ImpMaterial`에 금속-거칠기/노멀/오클루전/에미시브 맵을 담고 같은 PBR 블록으로. 이것은 Ray-MMD와 독립이라 앞당겨도 된다.
- **P7 검증/튜닝/문서/출시**: 9개 세트 렌더링 비교, 사이트 문서 4개 언어, 릴리즈 노트, 2.0.0 릴리즈.

## 7. 검증 방법과 지켜야 할 규율

- **비교는 반드시 같은 프레임으로**: `--seek <sec> --paused --no-physics --frames 60` 이상(`CLAUDE.md`의 "Running MMDX12.exe from the CLI"). `--autoplay`가 없으면 로비에서 멈춘다.
  빌드 디렉터리마다 `mmdx12.ini`가 다르니 ini를 맞추거나 CLI로 고정한다. 기준(HEAD) 빌드는 별도 디렉터리나 `git worktree`로 만들어 **비트 비교**한다(기본 룩 불변 증명).
- 한 번에 창 하나, 배치 실행 전에 사용자에게 알린다(메모리 `no-window-spam`). **사용자가 실행 중인 `MMDX12.exe`가 있을 수 있다(이 세션에서도 PID가 있었다). 죽이지 말고 `build_dev` 같은 다른 빌드 디렉터리를 쓴다.**
- 눈으로 보는 검증은 PNG를 Read로 열어서 한다(`captures/`는 git 무시). 이미지 비교는 PIL만 있다(numpy 없음).
- PT/GI는 컴파일만 해서는 안 된다. `--render pt`, `--offline-still`로 실제로 찍어 본다. 이 세션에서 PT 경로는 한 번 찍어 확인했고(`01_9001`) 오프라인 GI는 못 찍었다.
- 셰이더는 런타임 컴파일이라 `build*/bin/mmdx12.log`의 `[E]`를 매번 grep한다. 팩은 `pack_check <dir|zip> --compile`로 확인.
- 텍스처 VRAM과 로딩 시간을 반드시 측정한다(Alcander: 재질 52개). 측정 없이 "괜찮다"고 하지 않는다.
- 테스트 도구를 늘린다: 파서(`#define` 평가, `.emd` 매핑, 경로 해석) 단위 테스트와 라이브러리 전수 프로브. 기존 `pack_suggest_test`, `rest_pose_test` 등의 스타일을 따른다.
- 작업 분담: 사용자는 워커 위임을 적극 쓰라고 해 왔다(메모리 `worker-delegation`). 이 세션의 방식: `/opencode-delegate model:deepseek level:default review:smoke`로 명세를 주고, 관리자는 `smoke`
  검토 + 직접 렌더링 검증. 서브에이전트(Agent 도구)는 사용자가 원하지 않았다. 워커는 `build_dev`에서만 빌드시키고 MMDX12.exe를 실행하지 못하게 한다. 사용자 인터페이스 다듬기는 직접.
- 공개 저장소: 앱 레포(MMDX12)는 **public**, 웹 레포(MMDX12_Web)는 private. 푸시 전에 서버/로컬 경로를 스크럽한다(메모리 `scrub-before-publishing`). 라이브러리 에셋(`library/`)은 수정하지 않는다.
- 세션 마무리 = 작업트리 깨끗하게 커밋 + `progress.md`에 날짜별 요약 추가(메모리 `session-close-procedure`).

## 8. 하지 말 것

- 폴더/파일 이름 구조에 의존하는 감지, 특정 팩 ID나 특정 게임을 엔진에 박는 것, 모델 모양을 사용자가 고르기 전에 바꾸는 자동 적용.
- 기본 룩 변경, 기존 팩 룩 변경. `GpuVertex`(60B), `RtVertex`, `MaterialConstants`(256B), `RtGeometry`(192B)의 호환을 깨는 변경은 이유와 비교 증명이 있을 때만.
- Ray-MMD 컨트롤러(IBL/SSR/후처리)를 따라 만드는 것. 모피 셸 / 패럴랙스 / 효과 `.fx`를 이번 범위에 끌어들이는 것.
- Ray-MMD나 모델 작가의 코드/텍스처를 저장소에 복사하는 것. 구현은 의미를 읽고 직접 쓴다. 모델 텍스처는 재배포하지 않는다.
- 일정 때문에 PT/GI를 건너뛰는 것(이 2.0.0은 PT/GI가 핵심 차별점이다).
